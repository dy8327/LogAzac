# 검사 기준 복원

1차 분석 구조 개편 후 가격·상품명 변경 등이 기존 오류 집계 대신 상태 변화로 분류되고, 슬롯 누락 집계도 달라졌다. 기본 검사 경로를 개편 직전 커밋 `95207b15d0e12121036c1501e3842aea072de3e3`의 코드로 복원한다. 개편 커밋은 `4c8f90533233a751eb45142bf841d4d7a6925714`이다.

## 변경 범위

- `python/legacy/`의 10개 파일은 개편 직전 원본과 동일한 내용이다. `python/analyzer.py`는 같은 Python 프로세스를 이 원본 진입점으로 교체해 실행한다. Java의 프로세스 제한 시간과 출력 수집을 그대로 사용한다.
- 원래 응답에는 버전과 작업 목록이 없으므로 Java는 누락된 버전을 1로 해석한다. 성공·오류 건수와 결과 목록의 일치를 확인하고, 기존 트랜잭션 안에서 저장한다.
- 버전 2의 결과·작업·근거 조회는 유지한다. 결과 화면은 버전 1의 성공·오류·장비 집계를 표시하고, 버전 2의 작업 집계와 구분한다.
- 현재 DB의 추가 테이블·컬럼과 기존 검사이력을 보존한다. DB 초기화·역방향 DDL·기존 결과 수정은 포함하지 않는다.
- 1차 분석 코드는 `python/phase1_analyzer.py`에 보존한다. 기존 1차 분석 단위 테스트도 별도로 유지한다.

## 검증

Python 3.12에서 `python -m unittest discover -s python/tests -v`를 실행했다. 기존 32개 테스트, 원래 검사 기준 4개 테스트, 비공개 로그 12개를 원본 분석기와 비교하는 1개 테스트가 통과했다(총 37개). 일반 CI에서는 비공개 파일 비교만 생략한다.

비공개 로그 비교는 아래 환경변수를 설정하면 실행할 수 있다. 원문과 거래·장비 식별자는 저장소에 포함하지 않는다.

```bash
LOGAZAC_PRIVATE_SAMPLES=/path/to/samples LOGAZAC_BASELINE_ANALYZER=/path/to/original/python/analyzer.py python -m unittest discover -s python/tests -v
```

12개 모두 규칙 종류, 판정, 건수, 장비·슬롯, 줄 번호, 탐지값, 원본 근거를 포함한 JSON 전체가 개편 직전 버전과 일치했다. 원본에서 인식하지 않던 레코드까지 새로 정상으로 판정하지는 않는다. 결과가 0건인 경우도 원본 동작 그대로이며, 전체 파일의 정상 처리를 보장하지 않는다.

Java 통합 테스트에는 원본 응답 저장, 기존 버전 2 이력 보존, 집계 불일치 거부, 저장 실패 시 롤백, Python 기본 경로→DB→결과 화면 검증을 추가했다. 로컬 검증 환경에는 Java 17만 있어 Java 21/Maven 검증은 GitHub Actions에서 수행한다.

## 적용

검증한 소스는 `develop`의 `f2a8349a5d4342819755fbca229150dd032339bf`이며, 운영 브랜치 `master`의 `2e07d746c63f2ffba1167c169337f6b64db92b8b`와 파일 내용이 동일하다. 복원 PR은 이 `master` 커밋을 기준으로 한다. 운영 서버의 실제 소스 버전과 DB 상태는 별도로 확인해야 한다.

1. 복원 PR의 Java 21 CI 통과와 변경 내용을 확인한다.
2. 운영 전환 시 복원 PR을 `master`에 반영한다. 현재 저장소는 `master` 변경 시 자동 배포가 실행되므로, 검토용 브랜치와 PR 생성 단계에는 배포가 실행되지 않는다.
3. 자동 배포의 WAR 재빌드와 서비스 재시작 결과를 확인한다. `LOGAZAC_ANALYZER_PATH`가 저장소의 `python/analyzer.py`를 가리키는지 확인한다. 추가 SQL 실행은 필요하지 않다.
4. 문제가 있던 파일을 다시 업로드해 원래 기준의 새 검사이력을 생성하고 결과를 확인한다. 이미 저장된 잘못된 판정은 자동으로 덮어쓰지 않는다.

이 변경은 검토용 브랜치로 준비하며 운영 서버에 직접 접속하거나 배포하지 않는다.
