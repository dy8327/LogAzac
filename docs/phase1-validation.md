- GitHub Actions는 공개 합성 테스트와 Java 테스트만 실행하며 자동 배포를 활성화하지 않는다.

## 결과 계약과 호환성
schemaVersion=2. 기존 resultStatus를 SUCCESS/ERROR/CHANGE/UNKNOWN으로 확장했다. category, findingType, severity, operationId, 업무일, 거래 키 해시, 시간, 원인 코드, 이전/현재 값과 근거를 보존한다. 작업 결과는 ANALYSIS_OPERATIONS, 선택 규칙 결과는 DETECTION_RESULTS에 저장한다. 여러 줄 근거는 CLOB와 시작/끝 줄, 상태 비교 근거는 PREVIOUS_* 컬럼에 저장한다. 별도의 범용 이벤트/근거 테이블은 이번 단계에서 만들지 않았다.
물리 줄 수에서 정상 로그 수를 빼는 계산을 제거했다. 성공/실패/미확인 작업 요약은 규칙 활성 여부와 독립적으로 관측 작업에서 계산한다. ERROR_COUNT는 활성화된 규칙의 ERROR 결과 수다. 작업이 실패해도 분석 실행이 완료되면 INS_STATUS=COMPLETED이다.
기존 DB 코드 EXTERNAL_INTEGRATION은 SQL 재전송, EXTERNAL_RETRANSMISSION은 요청/응답 로그를 뜻한다. 이력 호환을 위해 코드와 모듈명은 유지하고 화면에서는 각각 외부 시스템 재전송 로그 / 외부 연동 데이터 로그로 표시한다. 복합 파일은 MIXED다.
카탈로그는 src/main/resources/analysis-rules.json이며 Python/Java가 함께 읽는다. 서버는 임의의 등록 패턴을 실행하지 않으며 카탈로그에 없는 규칙을 거부한다. 분석 시작 시 활성 규칙 스냅샷을 고정하고 저장 단계에서 활성 여부를 재조회하지 않는다. 설정 임계값 편집과 범용 사용자 정의 규칙 엔진은 후속 범위다.

## 배포 순서와 확인 사항
1. 기존 Oracle DB를 백업하고 DET_RULE_TYPE 중복을 확인한다. 중복이 있으면 마이그레이션은 DDL 전에 중단한다. 임의로 중복 행을 삭제하지 않는다.
2. 현재 develop의 DB 스키마에 db/migrations/20260917_phase1_analysis.sql을 SQLcl/SQL*Plus로 적용한다. 신규 스키마는 db/logazac_init.sql을 사용한다. DDL은 암묵적으로 커밋된다.
3. Python 디렉터리와 src/main/resources/analysis-rules.json을 포함한 같은 커밋의 저장소 및 WAR를 함께 배포한다. Python 실행 경로와 카탈로그 상대 위치를 유지한다.
4. 운영 Oracle에서 제약조건·CLOB 저장·기존 이력 조회·작은 익명화 샘플 재분석을 확인한 뒤 트래픽을 전환한다.
5. 문제가 생기면 이전 애플리케이션/Python을 함께 복원한다. 추가 컬럼/테이블은 즉시 삭제하지 않고 유지한다. 이전 앱은 신규 CHANGE/UNKNOWN 결과를 해석하지 못하므로 v2 이력 조회를 제한하고 복구 방침을 결정한다. 신규 규칙을 비활성화하되 변경 전 USE_YN 스냅샷을 기준으로 복원한다.

이번 작업에서는 운영 DB 변경·서버 배포·PR 병합을 실행하지 않았다. Oracle 마이그레이션 PL/SQL은 작성·검토했으나 운영 Oracle 실행 검증은 남아 있다. H2 통과가 Oracle 검증을 대체하지 않는다.

## 후속 범위
부분 수신임을 식별할 프로토콜 필드가 없는 상태 로그는 완전성 추정에 한계가 있어 슬롯 소실을 후보로 표시한다. 스냅샷 비교는 파일 순서를 따르되 시각이 역전되면 비교하지 않는다. 덤프의 첫 번째 일시와 TIME을 관측 시간으로 사용하며 타임존은 추정하지 않는다. 재전송은 관측 시도 단위이고 재시도 최종 성공/장비 전체 완료를 추정하지 않는다.
2차는 외부 연동 XML/POS 필수 필드·금액·수량 검증, 3차는 결제/VAN 승인·취소 상태 흐름이다. 원문/명세가 없는 프로토콜을 추정 구현하지 않았다. 공개 표시에는 알려진 업체·기관명과 일부 거래 필드를 치환하지만 범용 개인정보 익명화 도구는 아니므로 포트폴리오에는 합성 로그를 사용한다.
